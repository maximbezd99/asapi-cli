# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Primary human users are solo app developers, small app teams, and ASO
researchers who delegate App Store research to AI agents.

AI agents are active operators: they populate and query project data through
the local HTTP API and use the existing CLI for direct App Store queries.
Humans primarily inspect the resulting research through the web interface.

## Product Purpose

asapi is a local Apple App Store research workspace. It replaces scattered
agent-generated text files with structured, queryable project data while giving
humans a clear place to inspect apps, storefronts, reviews, regional popularity,
keywords, and recent history.

Success means an agent can maintain useful research through stable programmatic
interfaces and a human can understand the current state without reconstructing
the work from files or transcripts.

## Positioning

asapi combines a credential-free public App Store client with a local,
project-scoped research database. Its defining mechanism is a deliberate split
between agent operation through CLI and HTTP interfaces and human inspection
through a read-only web interface.

## Operating Context

Users install a single self-contained `asapi` binary and run
`asapi app serve`. The binary starts a local Axum server, exposes a JSON API,
and serves its embedded React application.

Research is organized into named projects. Each project owns an isolated SQLite
database. A Default project is created during initialization. App Store data is
storefront-specific; US is the default storefront unless another country is
explicitly selected.

Agents create and manage projects, tracked apps, storefronts, and keywords
through the API. Humans open the local web application to review the collected
state. Existing top-level CLI commands remain available for direct App Store
queries.

## Capabilities and Constraints

- The product is local-first, single-user, and does not require Apple
  credentials.
- The web interface is read-only for now. Project and research mutations are
  exposed through the HTTP API.
- Apps belong to projects and have one required main storefront. Additional
  storefronts can refresh automatically or only when explicitly requested or
  opened.
- Storefront-dependent app details, reviews, similar apps, in-app purchases,
  keyword rankings, and other fetched data must keep country context explicit.
- Regional popularity data helps users understand where an app has meaningful
  market presence.
- Main and opted-in storefronts refresh automatically when stale. Reviews use a
  24-hour refresh threshold and paginate lazily.
- App observations are retained for 30 days; upstream history cannot be
  backfilled.
- Keyword ranking results are shared and cached by normalized query and country
  within a project so multiple tracked apps do not repeat the same upstream
  request.
- Each project is stored in its own SQLite database under
  `asapi-storage/projects`. The default base is
  `~/.local/share/asapi-storage`; callers may provide an explicit base path.
- GitHub releases distribute platform-specific self-contained binaries with the
  React assets embedded at compile time.

## Brand Commitments

The product name is `asapi`, written in lowercase. The interface should remain
clean and minimal, with product language favoring direct operational clarity
over marketing language.

## Evidence on Hand

- The implemented CLI, local server, API, storage model, and React interface are
  present in `crates/` and `web/`.
- The API contract is generated by `crates/server/src/openapi.rs`.
- Public App Store data retrieved by the product provides the real app,
  storefront, review, popularity, ranking, and history content shown in the
  interface.
- No customer testimonials, adoption claims, proprietary benchmarks, or press
  evidence are currently present and future work must not fabricate them.

## Product Principles

1. Treat agents as first-class operators with stable, queryable interfaces.
2. Keep human inspection legible, trustworthy, and read-only unless the product
   direction explicitly changes.
3. Preserve project isolation and local ownership of research data.
4. Make storefront context explicit wherever it changes the meaning of data.
5. Cache and retain upstream observations carefully because historical App
   Store data cannot be fetched retroactively.
